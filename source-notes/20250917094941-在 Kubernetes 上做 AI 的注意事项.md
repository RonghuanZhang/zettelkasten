作者：Drishti Gupta，Google Cloud 高级云架构师

随着越来越多团队将生成式 AI（GenAI）集成到应用和工作流中，Kubernetes 自然成为首选平台。它是管理容器化工作负载的成熟方案，但 AI 工作负载有其特殊性。

以下是运行 AI 工作负载时需要考虑的要点，以及可用的相关工具。

## 1\. GenAI 工作负载需要事件驱动基础设施

GenAI 功能通常依赖用户输入、流数据或后台任务，要求基础设施响应快、可扩展且高效。

- **Knative Serving** ：适合基于 HTTP 的 GenAI 服务（如大语言模型 API）。请求来时自动扩容，空闲时缩容到零，节省 GPU 资源成本。
- **KEDA** ：基于外部事件源（Kafka、RabbitMQ、Prometheus）实现事件驱动自动扩容，补充 Knative 的触发范围。

两者结合，能快速响应，控制基础设施成本。

## 2\. 云原生环境下服务 LLM 的注意事项

云原生工具提供了应对以下问题的基础组件，关键是整合可扩展服务、可观测性和 DevOps 最佳实践。

- **自动扩缩容灵敏度** ：LLM 流量波动大，自动扩容需用自定义指标精准调节。
- KEDA：适合基于事件（如队列长度、token 使用量）扩容。
	- Knative Serving：基于实际 HTTP 流量扩缩容，空闲时缩到零，适合 API。
	- VPA：自动调整 Pod 的 CPU 和内存请求。
	- KServe：为 ML 设计，支持基于推理吞吐量或请求数的扩容。
- **可观测性与调试** ：GenAI 行为不透明，需要指标、追踪和反馈。
- OpenTelemetry：日志、指标、追踪一站式收集。
	- Prometheus：系统监控和告警。
- **Prompt 与模型漂移** ：提示词会老化或输出不稳定。
- Evidently AI：实时监控提示词或输入漂移。
	- Langfuse / PromptLayer：分析提示词表现和演变。
	- LLMGuard：为输出加护栏，确保结果安全合理。
- **资源密集度** ：合理调度避免浪费，LLM 对 GPU 和内存需求高。
- Karpenter 或 Cluster Autoscaler：自动添加所需节点（如 GPU 节点）。
	- Kubeflow Pipelines：基于 Kubernetes 容器的可扩展 ML 工作流部署。
	- Kueue：管理批处理任务队列，确保资源充足后启动大任务。
	- Kubernetes GPU 调度（设备插件）：利用标签选择器精准调度 Pod，申请特定资源。

## 3\. MLDevOps 逐渐成熟：不再只关注模型

GenAI 不仅仅是模型管理，还要处理提示词、路由、评估循环，且都需要版本控制、可观测和自动化。

1. **PromptOps - 提示词作为版本化资产** ：把提示词当代码管理，使用 GitOps 工具如 Argo CD 管理模板，借助 Argo Workflows 和 Prometheus/Grafana 做部署验证和监控。KServe 可动态提供版本化提示词服务。
2. **GenAI 影子部署** ：后台部署新提示或模型，监控表现后再正式推送。用 Istio、Knative（请求路由和扩缩容）和 KServe（模型生命周期管理）实现流量路由、拆分和影子支持。
3. **评估流水线 - 自动化模型和提示测试** ：持续评估保证质量。用 MLflow、Weights & Biases 记录模型和提示变更，Kubeflow Pipelines 管理 ML 原生工作流。

## 总结

在 Kubernetes 上运行 AI 不只是可行，更很强大。借助合适工具，你可以把提示词、模型和 GenAI 服务当作任何生产级软件组件管理。但这需要观念转变：提示词不只是字符串，是资产；评估不只是测试脚本，是流水线。拥抱云原生生态，让 AI 工作流与基础设施共同进化。
