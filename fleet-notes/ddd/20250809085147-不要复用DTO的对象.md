短答：**大多数情况下不要复用**。值对象（VO）属于领域层、表达不变的业务概念；而 **Cmd / Query / DTO** 属于用例/适配层，是**场景驱动的传输契约**。就算字段“长得像”，语义也常常不同，强行复用只会让边界变糊、演进变难。

—

# 为什么 VO 能复用而 Cmd/Query/DTO 不该随便复用

* **VO（领域层）**：不可变、具备业务不变量与行为，是**领域语言**的一部分，天然可在同一限界上下文内复用。
* **Cmd/Query/DTO（适配层 / 应用层）**：面向**用例**与**接口契约**，随接口演进而频繁变化；同字段 ≠ 同语义（Create 和 Update 的“name”常有不同约束）。跨用例复用会把一个对象绑死在多个场景上，导致牵一发而动全身。

# 在 COLA 里的位置与复用准则

* **COLA 分层**（简化）：`client(api)`（Cmd/Query/DTO 定义） → `app`（Use Case/Service） → `domain`（实体/VO/领域服务） → `infra`（Repo/Gateway）。
* **Cmd/Query/DTO 放在 client(api)**，是对外暴露的契约；**Assembler/Converter** 负责 client⇄domain 的转换。
* **准则**

  1. **按用例建模**：一个用例一个 Cmd/Query/DTO。
  2. **字段相同但语义不同 → 独立对象**（CreateUserCmd vs UpdateUserCmd）。
  3. **确有稳定“技术性”共性 → 抽共用组件**，例如分页、排序、时间范围这些**与业务无关**的技术性结构可以复用。
  4. **不要把领域 VO 直接暴露成 DTO**；用 Assembler 做映射，避免领域泄漏。
  5. **跨限界上下文禁止复用 DTO**；如需对接外部系统，用 **ACL/Anti‑Corruption Layer** 适配。
  6. \*\*共享内核（Shared Kernel）\*\*只留真正稳定且跨上下文一致的概念；慎之又慎。

# 可以复用的“安全带”

适合沉淀为公共模型的，多是“横切且技术性”的小结构：

```java
// client(api) 层
public class PageQuery {
    private Integer pageNo;
    private Integer pageSize;
}

public class SortOption {
    private String field;
    private String direction; // ASC/DESC
}

public class TimeRange {
    private Instant start;
    private Instant end;
}
```

在具体用例里**组合**而非继承：

```java
public class ListFunctionsQuery {
    private PageQuery page;
    private SortOption sort;
    private String runtime;      // 业务筛选字段
    private String status;       // 业务筛选字段
}
```

# 不要复用的典型场景

* `CreateServiceCmd` 和 `UpdateServiceCmd`：字段重叠，但**校验与必填**不同，应分开。
* `ServiceDTO`（对外展示）与 `Service`（领域实体）/ `ServiceVO`（值对象）：**生命周期、隐私与计算字段**不同，保持隔离。
* `SearchXXXQuery` 与 `ListXXXQuery`：即便都带分页，**过滤条件与索引策略**常不同，独立建模更清晰。

# 迁就复用会带来的坑

* 用例 A 改字段 → 用例 B、C 接口契约被动变更；
* DTO 被领域层引用，导致**双向依赖**和层间耦合；
* 测试与版本管理困难，发布风险放大。

# 实操建议

1. **优先独立**：为每个用例定义专属 Cmd/Query/DTO。
2. **抽“技术共性”**：分页、排序、通用时间段、通用响应包装可复用。
3. **Assembler 严格单向**：`Cmd/Query/DTO → Domain`、`Domain → DTO`，集中做字段/语义转换与校验。
4. **度量与演进**：当多个用例连续 3+ 次对同一块结构重复，且语义一致，再沉淀为公共组件。
