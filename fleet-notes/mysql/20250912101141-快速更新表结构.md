# ALGORITHM=INSTANT + LOCK=NONE 是什么

* **`ALGORITHM=INSTANT`**：让 `ALTER TABLE` 只改“**元数据**”，不重建表，不扫描数据页。对于 **InnoDB** 表，在支持的操作（如 **ADD COLUMN**）上几乎是“瞬时”完成；老数据行在读新列时返回默认值（并不会真的去改写每一行）。([MySQL][1])
* **`LOCK=NONE`**：在变更期间允许并发 **查询和写入（DML）** 正常进行（只会拿非常短暂的元数据锁来提交定义变化）。如果你指定了比该操作所需更“宽松”的锁级别，MySQL 会直接报错而不是退化到更重的锁。([MySQL][2])

# 什么时候真能“瞬时、不阻塞写入”

要满足这些版本与条件（否则就不是 INSTANT，或会失败）：

1. **存储引擎与版本**

* InnoDB + MySQL **8.0.12** 起支持 “Instant ADD COLUMN”；后续版本逐步增强。到 **8.4**，INSTANT 已成为默认算法（但**仍建议显式写出**以防回退/不支持时硬失败）。([MySQL][3])

2. **列位置限制（按版本）**

* **8.0.12–8.0.28**：只能**追加到表尾**（last column）才能用 INSTANT。
* **8.0.29+**：放到任意位置也可 INSTANT（官方做了优化）。([Oracle Blogs][4])

3. **操作的组合**

* **只做**支持 INSTANT 的动作（例如单独 `ADD COLUMN`）。**不要**和不支持 INSTANT 的改动（建索引、修改存储格式等）放在同一条语句里，否则整条语句就不是 INSTANT 了。([MySQL][5])

# 已知限制与注意点

* **自增列**：新增 `AUTO_INCREMENT` 列不走 INSTANT，至少需要 `INPLACE` 并带更强锁；可能触发表重建。([MySQL][5])
* **次数上限**：一个表经历的 **Instant ADD/DROP** 次数有上限（官方博客提到**最多 64 次**），超出会退化为更重的算法。([Oracle Blogs][6])
* **备份/生态**：历史上个别备份工具版本（如某些 XtraBackup 版本）对 8.0.29 初期的 INSTANT 有兼容性提示；生产前请验证你的备份链路。([docs.percona.com][7])

# 为什么还要显式写出它们

* 在 **8.4** 虽然默认就是 INSTANT，但**显式**写 `ALGORITHM=INSTANT, LOCK=NONE` 有两点好处：

  1. 若你的操作或目标版本**不支持**，SQL 会**报错**而不是静默回退到更慢、更阻塞的算法；
  2. 把“不会阻塞写入”的期望**写进代码/变更脚本**，便于 code review 与审计。([MySQL][5])

# 正确示例

```sql
ALTER TABLE application
  ADD COLUMN row_version BIGINT UNSIGNED NOT NULL DEFAULT 0
  COMMENT 'Optimistic lock version, incremented on each modification',
  ALGORITHM=INSTANT,
  LOCK=NONE;
```

* 在 **8.0.12–8.0.28**：确保 **追加到表尾**；
* 在 **8.0.29+**：任意位置也可，但依然建议只做“纯 ADD COLUMN”。([Oracle Blogs][4])

> 小结：`ALGORITHM=INSTANT, LOCK=NONE` 的组合就是把 **DDL 的侵入性降到最低**：元数据秒改、读写不停。前提是 **InnoDB + 合法的操作与版本**，且不要混搭其他非 INSTANT 变更。
