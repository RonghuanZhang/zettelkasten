答案：用**一个进程级 base logger**即可；按场景用两种传递法：**构造注入（首选）**和**context 传递（请求链路）**。全局变量可做兜底，不当主通道。

## 选择策略

- **1）构造注入 DI（优先）**  
    适合服务、仓储、任务等长期对象。可测试、可替换、无隐式依赖。
    
- **2）context 注入（请求链路必用）**  
    在 Gin 中间件基于 base logger `.With(request_id, trace_id, …)` 得到**子 logger**，放进 `context`，随调用链传递。保证每条日志都带请求字段。
    
- **3）全局 logger（兜底）**  
    `zap.ReplaceGlobals` 方便第三方或启动期无上下文代码调用 `zap.L()`。不要把**业务主路径**建立在全局上，避免隐式依赖与测试困难。
    
- **不要**：每个包自建包级全局 `var logger *zap.Logger`。难测、难热更新、字段不一致。
    

## 代码骨架

### 初始化一次（main）

```go
logger, level := logx.New(logx.Cfg{ /* ... */ }) // 进程唯一 base logger
_ = level // 可用于热切级别
```

### DI（首选）

```go
type Service struct{ log *zap.Logger }

func NewService(base *zap.Logger) *Service {
	return &Service{log: base.With(zap.String("comp", "service"))}
}

func (s *Service) Do(ctx context.Context, id string) {
	// 若有请求上下文字段，用 context 覆盖优先
	log := logx.FromContext(ctx).With(zap.String("comp", "service"))
	log.Info("doing", zap.String("id", id))
}
```

### Gin 中间件塞入请求子 logger

```go
func RequestLogger(base *zap.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		rid := ensureRequestID(c)
		reqLog := base.With(
			zap.String("request_id", rid),
			zap.String("method", c.Request.Method),
			zap.String("path", c.FullPath()),
		)
		ctx := logx.ToContext(c.Request.Context(), reqLog)
		c.Request = c.Request.WithContext(ctx)
		c.Next()
	}
}
```

### context 辅助

```go
// logx/context.go
type ctxKey struct{}
var k ctxKey

func ToContext(ctx context.Context, l *zap.Logger) context.Context {
	return context.WithValue(ctx, k, l)
}
func FromContext(ctx context.Context) *zap.Logger {
	if v := ctx.Value(k); v != nil {
		if l, ok := v.(*zap.Logger); ok { return l }
	}
	return zap.L() // 兜底：全局
}
```

## 何时用哪种

- **业务服务、DAO、Job**：构造注入 + 方法入参带 `context.Context`。
    
- **HTTP 调用链**：中间件放入**带请求字段**的子 logger 到 `context`，下游用 `FromContext`。
    
- **启动期、库代码、无 ctx 场景**：临时用 `zap.L()`。
    
- **协程**：启动 goroutine 时把**带字段的 ctx**一起传入，避免丢字段。
    

## 关键点

- 只建**一个 base logger**，下游用 `.With(...)` 派生子 logger，不重复创建核心。
    
- 请求字段放在**子 logger**里，不放全局。
    
- 不把 logger 长期存在全局或单例中；**per-call 用 context，per-component 用 DI**。
    
- 需要动态级别就用 `zap.AtomicLevel` 保存引用，提供切换端点。


`.With(...)` 是 Zap 的**字段预绑定**方法。它返回一个**子 logger**，这个子 logger 会在后续每条日志里自动带上这些字段；它与原 logger 共享相同的 Core，不会重复创建输出目标。

## 为什么要派生子 logger

- **避免重复**：组件名、请求 ID、租户 ID 等“恒定字段”不用每次 `Info(..., zap.String("request_id", rid))` 重复写。
    
- **一致性**：保证同一条请求或同一组件的所有日志字段一致，不会漏。
    
- **性能与安全**：Zap 的 logger 是不可变的；`.With` 返回新对象，原对象不变，线程安全；共享 Core，不额外打开文件或网络。
    
- **分层语义**：可以按“进程 → 组件 → 请求”逐层叠加字段，便于查询与聚合。
    

## 基本用法

```go
base := zap.L() // 进程级
svcLog := base.With(zap.String("comp", "order-service"))         // 组件级
reqLog := svcLog.With(zap.String("request_id", rid), zap.String("user", uid)) // 请求级

reqLog.Info("created")
```

等价于每次都写：

```go
base.Info("created",
  zap.String("comp","order-service"),
  zap.String("request_id", rid),
  zap.String("user", uid),
)
```

但子 logger更短、更不易漏字段。

## 典型分层

```go
// 进程启动
base := zap.New(core)

// 构造注入到组件
type Repo struct{ log *zap.Logger }
func NewRepo(base *zap.Logger) *Repo {
    return &Repo{ log: base.With(zap.String("comp","repo")) }
}

// 每个请求进入时再叠加请求字段
func handler(c *gin.Context, repo *Repo) {
    rid := ensureRID(c)
    log := repo.log.With(zap.String("request_id", rid))
    log.Info("handle_begin")
}
```

## `.With` vs `.WithOptions`

- **`With(fields...)`**：绑定**字段**到日志上下文（如 `request_id`）。
    
- **`WithOptions(opts...)`**：绑定**行为选项**（如 `AddCallerSkip`, `AddStacktrace`）。不增加字段。
    

## SugaredLogger 的 `With`

如果你在用 `SugaredLogger`：

```go
s := zap.S().With("comp", "svc", "request_id", rid)
s.Infow("ok") // 自动带 comp 和 request_id
```

原则相同，只是键值对形式。

## 何时用 `.With`

- 组件固定标签：`comp`, `module`, `version`
    
- 请求/任务范围标签：`request_id`, `trace_id`, `tenant_id`, `job_id`
    
- 长生命周期协程：在启动 goroutine 前先 `.With(job_id)` 再传入
    

## 何时不要用 `.With`

- **每条日志都变化的值**（如循环中的 `i`）直接放到该条日志的字段里，不要绑在子 logger 上，避免污染后续日志。
    

结论：用一个 base logger，按组件与请求**派生子 logger**，通过 `.With` 预绑定恒定字段，获得更少样板代码、更一致字段和更安全的并发行为。
