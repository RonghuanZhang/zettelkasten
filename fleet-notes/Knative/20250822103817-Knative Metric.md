很好！把 **Metric（autoscaling.internal.knative.dev）** 这类 CRD 放到整条链里看，会更清晰：

# 它的作用（一句话）

**Metric CRD = 给 KPA 提供“如何采集伸缩指标”的配置对象**：包括**从哪个 Service 抓指标**（`scrapeTarget`）以及**稳定/恐慌窗口**（`stableWindow` / `panicWindow`）。([knative.dev][1])

# 它在流程里怎么交互

1. **创建阶段**
   新 Revision 出来后，会有对应的 **PodAutoscaler（KPA）**。KPA 在调和时**创建/更新同名的 Metric 资源**，把：

   * `scrapeTarget` 设为该 Revision 的**指标服务**（KPA 状态里也会写出 `metricsServiceName`）；
   * `stableWindow` / `panicWindow` 设为当前生效的时间窗（来自 `config-autoscaler` 或注解覆盖）。
     这几个字段都在官方 API 里明确定义。([knative.dev][1])

2. **采集阶段（Metric 控制器）**
   **Metric 控制器**根据 Metric 的 `scrapeTarget` 去**抓取 queue-proxy/activator 汇报的并发或 RPS**，并按 **稳定窗/恐慌窗**聚合出观测值。KPA 就靠这些“窗口聚合后的指标”做判断。([knative.dev][2])

3. **决策与执行（KPA）**
   KPA 用观测值与 `target` 比较，算出 `desiredScale` & 是否进入 **panic 模式**；随后更新 Deployment 的副本数，并在需要时切 **SKS Serve/Proxy**（从而是否经 Activator）。这些行为也会以**控制面指标**暴露出来（如 `panic_mode`、`requested_pods` 等）。([knative.dev][3])

> 小提示：**Metric 只负责“怎么采、采多久”**；“按什么指标伸缩”由注解 `autoscaling.knative.dev/metric` 决定（KPA 支持 `concurrency` / `rps`，HPA 支持 `cpu`）。([knative.dev][4])

# 你能看到什么

* 列表与详情：

  ```bash
  kubectl -n <ns> get metric
  kubectl -n <ns> describe metric <revision-name>   # 通常与 Revision 同名
  ```

  里面能看到 `scrapeTarget`、`stableWindow`、`panicWindow` 等；在 KPA 的 `status` 里也能看到 `metricsServiceName`。([knative.dev][1])

# 怎么去抓取的？

很好，这两个问题本质上是“伸缩指标在哪里、怎么被抓”的事儿。给你结论版 + 可验证命令。

# 结论速读

* **queue-proxy / activator 并不会把伸缩指标长期“存”到某个库里**。它们在各自的 Pod 内**暴露可抓取的指标端点**（HTTP），**Autoscaler 在内存里按时间窗聚合**（稳定窗/恐慌窗），用于实时决策；若你想**持久化**，需要自己配 **Prometheus/OTel Collector** 去拉并保存，和 Autoscaler 决策解耦。([knative.dev][1])
* **Metric CRD 里的 `scrapeTarget`** 就是\*\*“告诉 Metric 控制器去哪个 K8s Service 抓指标”\*\*；而 **KPA（PodAutoscaler）会为每个 Revision 管一个“metrics Service”**，其名字写在 **`status.metricsServiceName`** 中，供 `scrapeTarget` 使用。([knative.dev][2])
* **抓取是直连 Pod 的，不经过 Activator**；**当没有 Pod 在跑时（scale-to-zero），也就没法抓**。此时由 **Activator 直接唤醒 Autoscaler**（不是靠抓取）。([Red Hat Docs][3], [knative.dev][4])

# 指标流转（一步步）

1. **KPA 调和**某个 Revision 时：

   * 生成/维护一个\*\*“metrics Service”\*\*（ClusterIP），并把其名字写进 **`KPA.status.metricsServiceName`**；
   * 创建/更新一个同名 **Metric 对象**，其 **`spec.scrapeTarget`** 指向上面的 Service，并写入 **`stableWindow`/`panicWindow`**。([knative.dev][2])
2. **Metric 控制器**依据 `scrapeTarget`，**定期抓取**该 Revision 的 queue-proxy（以及在需要时的 activator）暴露的并发/RPS，**按稳定/恐慌窗口聚合**成观测值。Autoscaler 自身也暴露了诸如 `scrape_time`、`stable_requests_per_second` 等控制面指标，能侧证“抓取确实在发生”。([knative.dev][5])
3. **KPA**用观测值对比你的 **`target`**，计算 **`desiredScale`**，并配合 SKS 切换 Serve/Proxy。([knative.dev][5])
4. **Scale-to-zero 场景**：没有 Pod ⇒ 无处可抓；当请求先打到 **Activator** 时，它**直接通知 Autoscaler 拉起副本**；待 Pod Ready 后，抓取才恢复。([Red Hat Docs][3], [knative.dev][4])

# 现场验证（3 条命令）

```bash
# 1) 查某 Revision 的 metrics Service 名
kubectl -n <ns> get kpa <revision> -o jsonpath='{.status.metricsServiceName}{"\n"}'

# 2) 看对应 Metric 对象的 scrapeTarget / 时间窗
kubectl -n <ns> get metric <revision> -o jsonpath='{.spec.scrapeTarget}{"\n"}{.spec.stableWindow}{"\n"}{.spec.panicWindow}{"\n"}'

# 3) 侧证 autoscaler 确实在抓取（控制面 metrics 有 scrape_time 等）
kubectl -n knative-serving logs deploy/autoscaler | grep -i scrape || true
```

# 小结口诀

* **数据驻留**：Autoscaler **内存窗口**（非持久化）；要长期留痕→用 **OTel/Prometheus**。([knative.dev][6])
* **抓取入口**：`Metric.spec.scrapeTarget` → 指向 **KPA 管的 metrics Service**。([knative.dev][2])
* **无 Pod 不抓取**；**scale-from-zero 靠 Activator 触发**。([Red Hat Docs][3], [knative.dev][4])
