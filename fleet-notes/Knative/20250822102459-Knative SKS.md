好问题！把 **谁会改 SKS、在什么情况下改** 说清楚👇

# 谁修改 SKS？

- **Knative Serving 的 autoscaler 组件**（部署名通常就叫 `autoscaler`）里的 **ServerlessService/KPA/HPA 控制器**。
    
    > 不是 Kourier，也不是 Activator。Kourier只转发流量；Activator只作为目标被指向。
    

# 什么时候会改？

1. **scale-to-zero / 没有就绪 Pod**
    
    - 触发：空闲降零；滚动发布空窗；镜像拉取/探针失败导致 Ready=0。
        
    - 动作：把 **SKS.mode 切到 `Proxy`**，Service Endpoints 指向 **Activator**。
        
2. **scale-from-zero / Pod 恢复就绪**
    
    - 触发：新 Pod Ready、可承载流量。
        
    - 动作：把 **SKS.mode 切回 `Serve`**，Endpoints 指向 **Revision Pod（queue-proxy）**。
        
3. **TBC（Target Burst Capacity）变化**
    
    - 触发：全局 `config-autoscaler` 或 Revision 注解更新。
        
    - 动作：根据取值决定是否让 Activator **常驻（-1）**、**仅冷启动进入（0）**，或在正数策略下更倾向经 Activator——从而更新 **SKS.mode** 与后端 Endpoints。
        
4. **新 Revision 初始/就绪过程**
    
    - 触发：你改了 `spec.template`，生成新 Revision。
        
    - 动作：为该 Revision **创建/更新 SKS**；就绪前多为 `Proxy`，就绪后切 `Serve`。
        

> 其它 autoscaling 注解（如 `minScale/maxScale/metric/target`）本身不会直接“改模式”，但会改变副本与就绪情况，**间接**引起 SKS 切换。

# 现场怎么确认是谁在改？

```bash
# 看 SKS 的 Owner（应是 PodAutoscaler）
kubectl -n <ns> get sks <revision-name> -o jsonpath='{.metadata.ownerReferences[0].kind}{" "}{.metadata.ownerReferences[0].name}{"\n"}'

# 看当前模式（Serve/Proxy）
kubectl -n <ns> get sks <revision-name> -o jsonpath='{.status.mode}{"\n"}'

# 看 autoscaler 是否在调和（修改 SKS 的控制面）
kubectl -n knative-serving logs deploy/autoscaler -f
```

单个小问（回“Serve”或“Proxy”即可）：  
当 **就绪 Pod=0** 时，`sks.status.mode` 一般会变成什么？


结论先给：**监听 SKS 并作出“实质响应”的是 Knative Serving 的 _ServerlessService Controller_（隶属 autoscaler 组件）**。  
它根据 SKS 的期望状态把 **Revision 的后端 Endpoints 切到 Activator（Proxy）或 Pod（Serve）**，并维护与之相关的 Service/Endpoints 对象。

顺带区分下“间接响应者”与“不相关者”：

- **Activator（间接）**：不监听 SKS 本身，主要监听 **Endpoints** 变化来更新自身的转发/节流（因此会“跟着”SKS 切换的结果行动）。
    
- **net-kourier-controller（不相关）**：监听的是 **KIngress**，把路由规则下发到 Envoy；**不**看 SKS。
    

你可以这样侧证：

```bash
# 看 SKS 的 Owner（通常是 PodAutoscaler）
kubectl -n <ns> get sks <rev> -o jsonpath='{.metadata.ownerReferences[0].kind}{" "}{.metadata.ownerReferences[0].name}{"\n"}'
# 看 autoscaler 是否在调和
kubectl -n knative-serving logs deploy/autoscaler -f
# 看切换结果（Serve/Proxy）
kubectl -n <ns> get sks <rev> -o jsonpath='{.status.mode}{"\n"}'
```

单个小问（回“是/否”即可）：**net-kourier-controller 会监听 SKS 吗？**


好问题。把这段“切到 Activator 后会发生什么”按时间线说清楚——也顺便回答 Route/KIngress 会不会被改：

# 流程（Kourier 场景）

1. **触发**  
    Autoscaler（准确说是 Serving 里的 _ServerlessService/PodAutoscaler 控制器_）发现 **Ready Pod=0** 或需经 Activator（例如 TBC=-1）。
    
2. **修改 SKS → Proxy**  
    它把 **SKS.mode=Proxy**，并把 **`<revision>-private` Service 的 Endpoints 改成指向 Activator**（而不是 Pod）。
    
3. **流量进 Activator（路由不变）**
    
    - Kourier/Envoy（由 net-kourier-controller 下发的配置）**仍按原路由规则**把请求导向 `<revision>-private`。
        
    - 因为该 Service 的 **Endpoints 已指向 Activator**，所以请求会到 Activator。
        
    - **Route 和 KIngress 都不需要修改**：域名/路径/权重没变，只是后端 Endpoints 变了。
        
4. **拉起/等待 Pod**  
    Autoscaler 设定期望副本数（KPA/HPA 写到 Deployment）。K8s 拉起新 Pod；Readiness 就绪后，Ready>0。
    
5. **切回直达**  
    Serving 控制器把 **SKS.mode 切回 `Serve`**，把 `<revision>-private` 的 Endpoints 改回 **指向 Revision Pod（queue-proxy）**。此时 Activator 退出链路（若 TBC=0 或合适的正数）。
    

# 谁改了什么？

- **改 SKS / Endpoints 的**：Serving 的 _ServerlessService/PodAutoscaler 控制器_（在 `autoscaler` 部署里）。
    
- **Route/KIngress**：**不会因“Pod 未就绪/就绪”而改**；只有当你改 `ksvc.spec.traffic` 或域名/证书等**路由层**配置时，**Route 控制器**才会更新 **KIngress**，再由 **net-kourier-controller**下发 Envoy。
    

# 现场验证（两条命令）

```bash
# 看 SKS 当前模式（Serve/Proxy）
kubectl -n <ns> get sks <revision> -o jsonpath='{.status.mode}{"\n"}'

# 观测 Endpoints 确实切到 Activator 或 Pod
kubectl -n <ns> get endpoints <revision>-private -o wide
```

小检查（回“会”或“不会”即可）：  
**仅仅因为 Pod 从 NotReady 变为 Ready，Route 或 KIngress 会被修改吗？**


**结论：**

* **谁创建 SKS？**——**Autoscaler** 部署里的伸缩控制面创建/维护（具体是 *KPA/ServerlessService* 相关的 reconciler）。KPA 在调和时会**创建/更新同名的 `ServerlessService`（SKS）**，并写入 `mode`（proxy/serve）等信息。([knative.dev][1])
* **它监听什么来创建？**——**监听 `PodAutoscaler（PA）` 的出现/变化** 来确保对应的 **SKS 存在并保持期望状态**；而 **PA 是由 Revision 的 reconciler 创建** 的（当新 Revision 生成时）。所以链路是：**Revision →（controller）→ PodAutoscaler →（autoscaler/KPA）→ SKS**。([knative.dev][1])

> 侧证：Knative 官方博客明确写到：创建新 Service 后，Configuration → Revision；**Revision 的 reconciler 会创建 `PodAutoscaler`**，随后 **KPA 会创建/更新 `ServerlessService`（SKS）**。([knative.dev][1])

```bash

```
