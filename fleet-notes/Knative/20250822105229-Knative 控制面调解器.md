好问题！下面把三个 Deployment 里各自到底“管”哪些 Reconciler，和它们在控制面/数据面的定位，一口气梳理清楚。

# knative-serving/controller 里有哪些 Reconciler（控制面）

运行在 `deploy/controller` 中的进程同时装配了多套 Serving 核心 Reconciler，主要包括（按资源维度）：

* **Service**：负责把 `ksvc` 展开成 `Configuration`、`Route` 等子资源。([Go Packages][1])
* **Configuration**：根据模板生成（并滚动）**Revision**。([Go Packages][1])
* **Revision**：对接 K8s Deployment/Pod 等工作负载对象。([Go Packages][1])
* **Route**：监听 `Route`，生成/对齐 **KIngress**（Knative 自己的 Ingress 抽象），用于后续网络层实现。([Go Packages][1])
* **DomainMapping**：自定义域名到 Route 的映射。([Go Packages][1])
* **Certificate / NSCert**：与证书相关（自动 TLS 体系的一部分）。([Go Packages][2])
* **GC（Garbage Collector）**：按策略清理不活跃的 Revision。([Go Packages][1], [knative.dev][3])
* **Labeler**：在 Configuration/Route 上补齐所需标签以支撑路由/滚动逻辑等。([Go Packages][1])

> 这些 Reconciler 都在 `knative.dev/serving/pkg/reconciler/...` 下可以找到，对应的包描述里明确了职责。([Go Packages][1])

# net-kourier-controller 里有哪些（控制面 → 驱动数据面的网关）

Kourier 是 Knative 的网络层实现之一：

* **Ingress（KIngress）Reconciler**：监听 **KIngress**，把期望路由/分流等配置翻译为 Envoy 的 xDS，并下发给 **kourier-gateway（Envoy）**。Repo 的 CI 日志和源码结构里都能看到 `pkg/reconciler/ingress`。([prow.knative.dev][4], [GitHub][5])
* 同时会**监听 Endpoints/Service 变化**以更新后端目标（Revision 的 public/private SVC/Endpoints），从而在 Pod 缩扩/切换 Proxy/Serve 模式时快速反映到网关。官方文档也说明“网络层的 controller 负责 watch KIngress 并据此配置 Ingress Gateway”。([GitHub][5], [knative.dev][6])

> 这里的 **net-kourier-controller 属于控制面**；真正转发请求的是 **kourier-gateway（Envoy）**，它属于**数据面**。([GitHub][5])

# autoscaler 里有哪些（控制面）

`deploy/autoscaler`（以及可选的 `autoscaler-hpa`）装配了与伸缩相关的 Reconciler/控制逻辑：

* **KPA（PodAutoscaler）Controller**：默认的伸缩器；依据并发/ RPS 等指标在稳定/恐慌窗口内计算期望副本数，并**决定 SKS 的模式（Proxy/Serve）**。([knative.dev][7])
* **SKS（ServerlessService）Controller**：根据 KPA 的决定，调谐 **public/private Service 的 Endpoints**，从而把流量指到 **Activator**（Proxy）或直接指向 **Pods**（Serve）。该控制逻辑在 autoscaling 基类中也能看到对 **Metric** 与 **SKS** 的调谐入口（`ReconcileMetric`/`ReconcileSKS`）。([Go Packages][8])
* **Metric Controller**：为每个 PA/Revision 管理 `autoscaling.internal.knative.dev/Metric` CR，指定 `scrapeTarget`（通常是 queue-proxy 暴露的 Svc），供 autoscaler 周期抓取/聚合指标。([knative.dev][9])
* **（可选）HPA Controller**：当使用 HPA 类（`autoscaling.knative.dev/class: hpa.autoscaling.knative.dev`）时生效，对接 K8s HPA 与 CPU 指标。([knative.dev][10])

> **Autoscaler 不在请求数据路径上，属于控制面**（读取指标→决策→更新副本数与 SKS/Endpoints）。数据面是 **Activator / queue-proxy / Ingress Gateway**。官方架构页把 Activator 明确为数据面、网络层 controller 负责网关配置，侧面印证 autoscaler 的控制面角色；“Activator 在数据面”一文也给出了全链路背景。([knative.dev][6])

你说的 “replicon” 应该是 **reconciler**。把这 4 个对象/角色的**关系与时序**捋清如下（以 KPA 为例）：

## 一条链路（谁监听谁、谁创建谁）

1. **Revision 出来后 → 创建 PodAutoscaler（PA/KPA）**
   `controller` 在生成 Revision 的同时也会生成 **PodAutoscaler**（PA）。随后 **KPA reconciler** 被触发开始调和该 PA。([knative.dev][1])

2. **KPA reconciler 调和 PA：产出 Metric + SKS，并算期望副本**

   * **创建/更新 Metric**（写好 `scrapeTarget` 与稳定/恐慌窗口，供采集器抓指标）；
   * **创建/更新 ServerlessService（SKS）**，并在 SKS 里记录**运行模式**（`proxy/serve`）与需要的 activator 数量；
   * **更新 Deployment 副本数**与 PA 状态。([knative.dev][1])

3. **SKS reconciler 调和 SKS：落地 public/private Service 与 Endpoints**

   * **创建两个 K8s Service**：`<rev>`（public，无 selector）与 `<rev>-private`（private，有 selector 指向 Pod）；
   * 根据 **SKS.spec.mode** 切换 **public Service 的 Endpoints**：

     * `Serve` ⇒ public 的 Endpoints = **`<rev>-private` 的 Pod IP 列表**；
     * `Proxy` ⇒ public 的 Endpoints = **Activator** 的 IP 列表。([knative.dev][1])

4. **PA 与 SKS 的“归属/指向”关系**

   * 在 **PA.status** 里会写出：

     * `serviceName`（“服务这个 revision 的 K8s Service 名”）——**由此 PA 拥有的 SKS 创建/管理**；
     * `metricsServiceName`（采指标用的 Service）。([knative.dev][2])

> 小结：**PA 的变化 → 触发 KPA reconciler → 生成/更新 Metric & SKS；
> SKS 的变化 → 触发 SKS reconciler → 创建/切换 public/private Service 与 Endpoints。**
> Activator 是否在链路上，取决于 **SKS.mode**；并不需要改 Route/KIngress。

你说的 “replicon” 应该是 **reconciler**。下面把 **PodAutoscaler（PA）/ SKS / Metric** 这三个 CRD，和 **autoscaler** 里的 **KPA reconciler / SKS reconciler / Metric reconciler** 的**关系与时序**一次讲清：

# 一句话总览

**Revision 生成 → Controller 创建 PodAutoscaler（PA） → KPA reconciler 调和 PA：产出/更新 Metric 与 SKS + 计算期望副本 → Metric reconciler 按 `scrapeTarget` 抓/聚合指标 → KPA 用指标算副本与是否进恐慌窗 → SKS reconciler 依 `SKS.spec.mode` 切 public Service 的 Endpoints（Activator 或 Pod）**。

---

# 谁监听谁 & 谁创建谁

* **Revision →（controller）→ PodAutoscaler（PA）**
  *PA 是后续伸缩与流量是否经 Activator 的锚点。*
* **KPA reconciler（在 `deploy/autoscaler`）监听：PA**

  * **创建/更新 `Metric`**（owner=PA）：填 `spec.scrapeTarget`、`stableWindow`、`panicWindow`。
  * **创建/更新 `SKS`**（owner=PA）：设置 `spec.mode`（`Serve`/`Proxy`）、需要的 activator 数量。
  * **更新 Deployment 副本数**（desired replicas）。
* **Metric reconciler（`autoscaler` 内）监听：Metric**

  * 按 `scrapeTarget` **抓 queue-proxy/activator 的指标**，按“稳定/恐慌”窗口**在内存聚合**，为 KPA 提供观测值。
* **SKS reconciler（`autoscaler` 内）监听：SKS**

  * 维护两个 K8s Service：`<rev>`（public，无 selector）和 `<rev>-private`（private，有 selector 指向该 Revision 的 Pod）。
  * 依 `SKS.spec.mode` **改写 `<rev>` 的 Endpoints**：

    * **Serve**：复制 `<rev>-private` 的 Pod IP 列表（直达 Pod/queue-proxy）。
    * **Proxy**：改为 **Activator** 的 IP 列表（先经 Activator）。

> **Owner 关系（很关键）**
> PA → 拥有 **Metric**、**SKS**；
> SKS → 拥有 **`<rev>`（public）** 与 **`<rev>-private`（private）** 两个 Service。

# 端到端时序（缩写版）

```
Controller:   Revision ──▶ PodAutoscaler(PA)
Autoscaler:   KPA Reconciler(看PA) ──▶ Metric(抓指标) & SKS(定mode) ──▶ 期望副本
              Metric Reconciler(看Metric) ──▶ 抓取/聚合 指标（内存窗口）
              SKS Reconciler(看SKS) ──▶ <rev>(public) Endpoints = Activator 或 <rev>-private
Data Plane:   Envoy(Kourier) ─▶ 命中 <rev>(public) ─▶ (按 Endpoints) Activator 或 Pod
```

---

# 典型状态切换

* **Ready Pod = 0 / 冷启动 / TBC=-1**
  KPA 把 **`SKS.mode=Proxy`** → SKS 把 **public Endpoints 指向 Activator** → 流量经 Activator，KPA 提升副本。
* **Pod Ready > 0 & 稳定**
  KPA 把 **`SKS.mode=Serve`** → SKS 把 **public Endpoints 复制 private 的 Pod IP** → 直达 Pod，旁路 Activator（若 TBC=0）。

# 小结要点

* **KPA reconciler**：核心大脑（看 PA → 产出 Metric/SKS → 算副本 & 决定 Proxy/Serve）。
* **Metric reconciler**：把 *怎么抓/抓多久* 落地，并持续提供窗口化观测值（内存聚合）。
* **SKS reconciler**：把 **Proxy/Serve 的策略**落到**public Service 的 Endpoints**切换上。
* **Autoscaler 整体是控制面**；真正转发流量的是数据面（Envoy/kourier-gateway、Activator、queue-proxy）。
