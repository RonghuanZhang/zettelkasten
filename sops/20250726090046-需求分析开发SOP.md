## 2. 目的（Purpose）

规范从需求分析到代码落地并可测试的全流程操作，确保团队在各阶段协作高效、输出质量可控。

---

## 3. 范围（Scope）

适用于公司内部软件项目的敏捷开发流程，包括需求收集、架构设计、编码实现、单元测试与集成测试准备。

---

## 4. 术语与定义（Definitions）

* **PO（Product Owner）**：产品负责人，负责需求优先级。
* **PM（Project Manager）**：项目经理，统筹进度与资源。
* **开发者**：负责编码与单元测试。
* **架构师**：负责系统设计与技术选型。
* **PR（Pull Request）**：代码合并请求。
* **CI（Continuous Integration）**：持续集成。
* **Unit Test**：单元测试。

---

## 5. 职责（Responsibilities）

| 角色    | 职责                           |
| ----- | ---------------------------- |
| PO    | 收集、澄清需求；制定优先级；验收需求文档         |
| PM    | 制定项目里程碑；跟踪进度；协调资源            |
| 架构师   | 输出系统高层设计与技术选型；评审关键设计方案       |
| 开发者   | 编写代码；撰写单元测试；按照PR规范提交流程       |
| 测试工程师 | 制定测试计划；设计集成/系统测试用例；执行测试并反馈缺陷 |
| CI管理员 | 配置并维护CI流水线；集成代码质量扫描与自动化测试    |

## 6. 操作流程（Procedures）

### 6.1 需求分析

1. **需求收集**：PO 与业务/客户沟通，形成初步需求列表。
2. **需求澄清会**：召集 PO、PM、架构师、开发者，评审需求可行性，补充细节。
3. **拆解与估算**：将大需求拆分为用户故事（User Stories）或任务，开发者与架构师给出评估工时。
4. **优先级排序**：PO 根据业务价值与风险，对用户故事进行排序。
5. **输出文档**：形成《需求规格说明书（SRS）》，记录功能点、验收标准和边界条件。

### 6.2 架构设计

1. **总体设计**：架构师输出系统上下游交互图、模块划分与技术栈选型。
2. **详细设计**：针对每个模块绘制类图/时序图或API接口定义文档（OpenAPI、接口契约）。
3. **设计评审**：组织架构师与开发者评审会议，确认设计满足性能、安全和可扩展性要求。
4. **更新文档**：根据评审反馈完善《系统设计文档（SDD）》。

### 6.3 编码实现

1. **创建分支**：基于主分支（master/main）创建 feature 分支，命名规范 `feature/ISSUE-编号-描述`。
2. **开发规范**：遵守编码规范（如 Java Code Style），编写自说明性代码，并添加必要注释。
3. **单元测试**：为核心逻辑编写覆盖率不低于 80% 的单元测试，使用 JUnit/TestNG。
4. **静态扫描**：本地执行代码质量工具（SonarLint/Checkstyle），修复高优先级告警。
5. **提交 PR**：按模板填写 PR 描述，包括变更范围、测试步骤、影响评估。

### 6.4 代码评审与合并

1. **自动触发 CI**：PR 提交后，CI 流水线自动编译、静态扫描和运行单元测试。
2. **人工评审**：至少两名同组开发者或架构师审阅，关注代码安全、性能和可维护性。
3. **修订与复审**：根据评审意见更新代码并推送，直至评审通过。
4. **合并**：Review 完成后，由 CI 管理员或拥有权限的开发者合并至主分支，触发集成测试流水线。

### 6.5 测试与验证

1. **环境准备**：CI 管道部署应用至测试环境（或使用容器编排），并初始化测试数据。
2. **集成测试**：测试工程师执行接口测试和集成测试用例，检查端到端流程。
3. **缺陷跟踪**：通过缺陷管理系统（JIRA/Bugzilla）记录问题并指派开发者修复。
4. **回归测试**：验证缺陷修复后，用例通过率需达到 100%。
5. **测试报告**：测试工程师输出《测试报告》，包含执行情况、缺陷统计与风险评估。

### 6.6 发布前准备

1. **UAT 验收**：与业务方进行用户验收测试，得到最终签字。
2. **版本打标**：在主分支打 Git Tag: `v{版本号}`。
3. **发布文档**：编写《发布说明》，包括新特性、改动说明、回滚指导。
4. **部署审批**：PM 审批后，交由运维团队或自动化脚本进行正式环境部署。

## 7. 风险及应对（Risks & Mitigations）

| 风险        | 应对措施                    |
| --------- | ----------------------- |
| 需求频繁变更    | 建立变更控制流程，评估影响并更新计划      |
| 设计缺陷导致返工  | 定期设计评审，模拟关键场景           |
| 自动化测试覆盖不足 | 扩充测试用例库，纳入压力和安全自动化测试    |
| 环境不一致     | 使用容器化/基础设施即代码（IaC）保证一致性 |

---

## 8. 质量控制与衡量（Quality & Metrics）

* **需求准确率**：一迭代内需求返工率 < 5%
* **代码覆盖率**：单元测试覆盖率 ≥ 80%
* **PR 通过率**：首次评审通过率 ≥ 70%
* **缺陷密度**：发布 1KLOC 缺陷数 ≤ 1
* **交付周期**：单个用户故事平均实现周期 ≤ 3 天

# 新版本

下面给你一条从“想法”到“上线”的可执行时间线。每一步写清：输入、关键动作、输出、负责人、退出条件。按中小型后端+前端产品的常见节奏规划为 0～12 周，可并行可裁剪。

# 0. 机会界定（W0）

- 输入：问题陈述、目标用户画像、业务目标（如营收/留存/成本）
    
- 动作：访谈 5–10 位目标用户；竞品快速拆解；定义成功度量（1–3 个北极星+3–5 个指标）
    
- 输出：一页纸《机会评估》（问题、受众、假设、指标、范围）
    
- 负责人：产品
    
- 退出条件：业务负责人或团队共识通过
    

# 1. 范围与PRD（W0–W1）

- 输入：机会评估
    
- 动作：列出核心用户旅程；分解为 MVP 能力与可延后项
    
- 输出：PRD v1（目标、用户故事、验收标准、非功能需求、度量指标、边界/不做清单）
    
- 负责人：产品
    
- 退出条件：PRD 评审通过（产品/研发/设计/数据共同签字）
    

# 2. 体验设计（W1–W2）

- 输入：PRD v1
    
- 动作：信息架构、低保真线框、关键流程原型；可用性快测
    
- 输出：交互稿、UI 规范、组件清单
    
- 负责人：设计
    
- 退出条件：关键流程可点击原型评审通过
    

# 3. 技术预研与技术方案（W1–W2）

- 输入：PRD、交互草图
    
- 动作：架构选型与权衡；数据模型；接口定义；依赖清单；风险与替代方案；PoC 验证不确定点
    
- 输出：技术方案/Design Doc（架构图、API 合同、表结构、容量预估、风险矩阵、里程碑）
    
- 负责人：研发（架构/后端牵头）
    
- 退出条件：技术评审通过（含安全、数据、SRE）
    

# 4. 计划与分解（W2）

- 输入：PRD、技术方案
    
- 动作：拆解为任务卡；估时；确定里程碑；排产；确定研发–设计–测试同步点
    
- 输出：甘特/里程碑、迭代 Backlog、责任矩阵（RACI）
    
- 负责人：研发+产品
    
- 退出条件：里程碑与资源确认
    

# 5. 基础设施准备（W2）

- 输入：技术方案
    
- 动作：仓库与分支策略；代码规范；CI/CD 流水线；运行环境/IaC；密钥与配置管理；监控告警基线
    
- 输出：可跑的脚手架与流水线（编译→测试→制品→镜像→部署到 Dev）
    
- 负责人：研发+SRE
    
- 退出条件：空仓示例服务能从提交到 Dev 可访问
    

# 6. 迭代开发（W2–W8，2周一迭代）

- 输入：Backlog、设计稿
    
- 动作：按用户旅程优先顺序实现；接口对齐；代码评审；单元/集成测试≥80% 关键路径覆盖
    
- 输出：每迭代可演示的增量版本；变更日志
    
- 负责人：研发
    
- 退出条件：迭代评审通过，关键故事满足验收标准
    

# 7. 测试与质量保证（W4–W9，与开发交错）

- 输入：可部署包、测试用例
    
- 动作：功能测试、接口契约测试、E2E、回归；性能基准（P95/P99、QPS、资源）；兼容性与灰度演练
    
- 输出：测试报告、缺陷清单与修复记录
    
- 负责人：QA（无专职则研发负责）
    
- 退出条件：关键缺陷清零；性能达标；回归通过
    

# 8. 安全与合规（W4–W9）

- 输入：技术方案与实现
    
- 动作：威胁建模；依赖漏洞扫描；密钥轮换策略；权限与审计；隐私与数据最小化
    
- 输出：安全评审记录、整改项已关闭
    
- 负责人：安全/研发
    
- 退出条件：高风险项清零，中风险有缓解方案与时间表
    

# 9. 数据与度量接入（W6–W9）

- 输入：PRD 指标、埋点方案
    
- 动作：事件埋点、日志结构化、看板配置、告警阈值
    
- 输出：指标看板（产品与SRE）、告警规则
    
- 负责人：数据/研发/SRE
    
- 退出条件：预发布环境可看到真实数据流
    

# 10. 预发布与UAT（W8–W10）

- 输入：候选版本 RC
    
- 动作：部署到 Staging；业务方/核心用户 UAT；Beta/灰度试点
    
- 输出：UAT 反馈与修复清单、发布候选 RC+
    
- 负责人：产品+研发
    
- 退出条件：UAT 关键问题关闭，发布门（release gate）通过
    

# 11. 上线准备（W10）

- 输入：RC、运维材料
    
- 动作：运行手册与应急预案；回滚策略验证；容量与成本复核；变更窗口预约
    
- 输出：Runbook、回滚脚本、变更计划（含沟通稿）
    
- 负责人：SRE+研发
    
- 退出条件：上线评审会通过
    

# 12. 上线与灰度（W10–W11）

- 输入：变更计划
    
- 动作：分批/按流量权重灰度；监控三色灯；SLO 观察；必要时自动回滚
    
- 输出：生产版本上线，灰度→全量记录
    
- 负责人：SRE（研发在岗支持）
    
- 退出条件：SLO 稳定≥24–48h，关键指标无退化
    

# 13. 上线后验证与迭代（W11–W12）

- 输入：上线数据与用户反馈
    
- 动作：与预设指标对比；问题复盘；下一轮增量规划
    
- 输出：上线复盘报告、后续 Roadmap
    
- 负责人：产品+研发+SRE
    
- 退出条件：复盘完成并登记改进项

## 可直接落地的简版模板

**PRD 骨架**

```
1. 背景与目标
2. 用户画像与场景
3. 核心流程（泳道/流程图）
4. 需求列表（用户故事 + 验收标准）
5. 非功能需求（性能、可靠性、安全、合规）
6. 指标与度量（北极星 + 辅助指标）
7. 范围界定（不做清单）
8. 里程碑与风险
```

**技术方案骨架**

```
1. 目标与约束
2. 架构图与组件职责
3. 数据模型与存储方案
4. API 合同（请求/响应/错误码）
5. 容量与性能预估（QPS、P95、资源）
6. 可靠性与SLO（可用性、降级、重试/幂等）
7. 安全与合规（鉴权、审计、数据分类）
8. 运维（CI/CD、监控、告警、日志、Runbook）
9. 风险与替代方案
```

**上线清单（节选）**

- 回滚验证通过（脚本/镜像/DB 变更有逆向方案）
    
- 监控就绪（可用性、错误率、延迟、业务指标）
    
- 告警阈值与值班人确认
    
- 变更沟通稿与FAQ
    
- 数据迁移脚本演练记录
    
- 灰度计划与终止条件

## 工程实践基线

- 分支策略：main 受保护，feature 分支 + PR 审核
    
- CI：编译→静态检查→单元测试→制品→镜像签名→镜像扫描
    
- CD：Dev→Staging→Prod 分环境，Prod 仅允许来自打了 tag 的 RC
    
- 质量门：覆盖率门槛、漏洞门槛、变更大小限制、变更冻结窗口
    
- 观测性：结构化日志、分布式追踪、指标三件套，SLO/告警绑定责任人
