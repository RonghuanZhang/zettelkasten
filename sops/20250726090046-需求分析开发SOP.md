## 2. 目的（Purpose）

规范从需求分析到代码落地并可测试的全流程操作，确保团队在各阶段协作高效、输出质量可控。

---

## 3. 范围（Scope）

适用于公司内部软件项目的敏捷开发流程，包括需求收集、架构设计、编码实现、单元测试与集成测试准备。

---

## 4. 术语与定义（Definitions）

* **PO（Product Owner）**：产品负责人，负责需求优先级。
* **PM（Project Manager）**：项目经理，统筹进度与资源。
* **开发者**：负责编码与单元测试。
* **架构师**：负责系统设计与技术选型。
* **PR（Pull Request）**：代码合并请求。
* **CI（Continuous Integration）**：持续集成。
* **Unit Test**：单元测试。

---

## 5. 职责（Responsibilities）

| 角色    | 职责                           |
| ----- | ---------------------------- |
| PO    | 收集、澄清需求；制定优先级；验收需求文档         |
| PM    | 制定项目里程碑；跟踪进度；协调资源            |
| 架构师   | 输出系统高层设计与技术选型；评审关键设计方案       |
| 开发者   | 编写代码；撰写单元测试；按照PR规范提交流程       |
| 测试工程师 | 制定测试计划；设计集成/系统测试用例；执行测试并反馈缺陷 |
| CI管理员 | 配置并维护CI流水线；集成代码质量扫描与自动化测试    |

## 6. 操作流程（Procedures）

### 6.1 需求分析

1. **需求收集**：PO 与业务/客户沟通，形成初步需求列表。
2. **需求澄清会**：召集 PO、PM、架构师、开发者，评审需求可行性，补充细节。
3. **拆解与估算**：将大需求拆分为用户故事（User Stories）或任务，开发者与架构师给出评估工时。
4. **优先级排序**：PO 根据业务价值与风险，对用户故事进行排序。
5. **输出文档**：形成《需求规格说明书（SRS）》，记录功能点、验收标准和边界条件。

### 6.2 架构设计

1. **总体设计**：架构师输出系统上下游交互图、模块划分与技术栈选型。
2. **详细设计**：针对每个模块绘制类图/时序图或API接口定义文档（OpenAPI、接口契约）。
3. **设计评审**：组织架构师与开发者评审会议，确认设计满足性能、安全和可扩展性要求。
4. **更新文档**：根据评审反馈完善《系统设计文档（SDD）》。

### 6.3 编码实现

1. **创建分支**：基于主分支（master/main）创建 feature 分支，命名规范 `feature/ISSUE-编号-描述`。
2. **开发规范**：遵守编码规范（如 Java Code Style），编写自说明性代码，并添加必要注释。
3. **单元测试**：为核心逻辑编写覆盖率不低于 80% 的单元测试，使用 JUnit/TestNG。
4. **静态扫描**：本地执行代码质量工具（SonarLint/Checkstyle），修复高优先级告警。
5. **提交 PR**：按模板填写 PR 描述，包括变更范围、测试步骤、影响评估。

### 6.4 代码评审与合并

1. **自动触发 CI**：PR 提交后，CI 流水线自动编译、静态扫描和运行单元测试。
2. **人工评审**：至少两名同组开发者或架构师审阅，关注代码安全、性能和可维护性。
3. **修订与复审**：根据评审意见更新代码并推送，直至评审通过。
4. **合并**：Review 完成后，由 CI 管理员或拥有权限的开发者合并至主分支，触发集成测试流水线。

### 6.5 测试与验证

1. **环境准备**：CI 管道部署应用至测试环境（或使用容器编排），并初始化测试数据。
2. **集成测试**：测试工程师执行接口测试和集成测试用例，检查端到端流程。
3. **缺陷跟踪**：通过缺陷管理系统（JIRA/Bugzilla）记录问题并指派开发者修复。
4. **回归测试**：验证缺陷修复后，用例通过率需达到 100%。
5. **测试报告**：测试工程师输出《测试报告》，包含执行情况、缺陷统计与风险评估。

### 6.6 发布前准备

1. **UAT 验收**：与业务方进行用户验收测试，得到最终签字。
2. **版本打标**：在主分支打 Git Tag: `v{版本号}`。
3. **发布文档**：编写《发布说明》，包括新特性、改动说明、回滚指导。
4. **部署审批**：PM 审批后，交由运维团队或自动化脚本进行正式环境部署。

## 7. 风险及应对（Risks & Mitigations）

| 风险        | 应对措施                    |
| --------- | ----------------------- |
| 需求频繁变更    | 建立变更控制流程，评估影响并更新计划      |
| 设计缺陷导致返工  | 定期设计评审，模拟关键场景           |
| 自动化测试覆盖不足 | 扩充测试用例库，纳入压力和安全自动化测试    |
| 环境不一致     | 使用容器化/基础设施即代码（IaC）保证一致性 |

---

## 8. 质量控制与衡量（Quality & Metrics）

* **需求准确率**：一迭代内需求返工率 < 5%
* **代码覆盖率**：单元测试覆盖率 ≥ 80%
* **PR 通过率**：首次评审通过率 ≥ 70%
* **缺陷密度**：发布 1KLOC 缺陷数 ≤ 1
* **交付周期**：单个用户故事平均实现周期 ≤ 3 天
